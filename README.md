# 本地协同文本 CRDT 引擎

一个**完全本地**的协同文本 CRDT（Conflict-free Replicated Data Type）引擎，用来模拟多个离线副本（replica）并发编辑同一份文档，并验证在任意消息顺序、重复投递、网络分区、进程重启之后所有副本最终收敛为相同文本。

- **零依赖**：仅使用 Node.js 内置能力（`node:fs`、`node:crypto`、内置测试运行器）。
- **无外部服务**：没有 WebSocket、HTTP、数据库、云协同平台。所谓“消息传递”只是在进程内把操作对象从一个副本交给另一个副本；持久化就是本地 JSON 文件。
- **终端可测**：`npm test`（底层为 `node --test`），不需要浏览器。

## 快速开始

```bash
node examples/demo.js   # 不需要 npm install
npm test                # 运行全部自动化测试
```

基本用法：

```js
import { Replica } from './src/crdt.js';

const a = new Replica('r1');
const b = new Replica('r2');

a.appendText('Hello');
b.pullFrom(a);            // b 获得 a 的全部操作 -> "Hello"

// 离线并发编辑
a.insertText(5, '!');     // a: Hello!
b.insertText(5, '?');     // b: Hello?

a.sync(b);                // 反熵交换（纯本地对象传递）
a.text() === b.text();    // true —— 收敛（结果为 "Hello!?"，规则见下）
```

## CRDT 模型：RGA + tombstone

引擎实现的是 **RGA（Replicated Growable Array，复制可增长数组）**：

- 文档是一棵以虚拟节点 `ROOT` 为根的**有序树**。每个存活字符是一个节点。
- 插入一个字符时，必须指明它的**左锚点** `afterId`（插入位置左边那个字符的 ID；文档开头为 `ROOT`）。新字符成为锚点节点的孩子。
- 一次插入多个字符（`insertText(index, text)`）时，字符按输入顺序首尾相接：后一个字符以前一个新字符为锚点，因此多字符插入是**整块连续**的，结果与把它拆成多次单字符插入完全一致。
- 删除是**逻辑删除**：节点保留在树中，仅置 `deleted = true`（tombstone，墓碑）。读取时跳过墓碑。这样即使删除操作比插入先到、或操作乱序投递，整合过程也不需要回滚。
- 读取顺序是对该树做深度优先遍历（DFS 先序）得到的全序。

### 稳定的全局操作 ID

每个操作（insert / delete）都有全局唯一且永不复用的稳定 ID：

```jsonc
{ "counter": 7, "replicaId": "r1", "lamport": 12 }
```

- `replicaId`：副本标识（构造时自动生成的随机串，或自行指定）。
- `counter`：该副本内从 1 开始的单调递增序号。`(replicaId, counter)` 构成全局唯一键（序列化形式 `"7@r1"`）。
- `lamport`：[Lamport 时间戳](https://en.wikipedia.org/wiki/Lamport_timestamp)，用于并发操作的全局排序。本地操作取 `max(本地时钟, 见过的最大时间戳) + 1`。

操作一旦产生，其 ID 与锚点关系永不改变 —— 这是去重、乱序整合、重启恢复的基础。

## 操作排序规则（收敛性的关键）

同一个锚点下可能有多个副本**并发**插入（例如都在第 3 个字符后插入）。兄弟节点按下面的**全序**确定性排列，与操作到达的先后顺序完全无关：

1. **Lamport 时间戳大者在前**（RGA 约定：逻辑上“更晚发起”的插入更靠左）；
2. 时间戳相同（真正并发）时，**副本 ID 字典序小者在前**；
3. 仍相同（理论上同一副本内不会出现）时按 counter 决胜。

因此任意两个副本，无论以何种顺序收到操作，对同一棵树排出来的顺序必然相同。并发插入/删除的典型结果：

| 场景 | 结果 |
|---|---|
| r1、r2 同在 `abc` 末尾插入 `X` / `Y`（lamport 相同） | `abcXY`（r1 < r2 字典序） |
| r1 删 `b`，r2 同时在 `b` 后插 `X` | `aXc`（`b` 成墓碑，`X` 仍挂在其下，顺序保留） |
| 两边删除同一个字符 | 删除幂等，结果正确 |

## 合并规则

- **去重**：每个副本维护已见操作集合 `seen`（opId）。重复接收同一操作直接忽略，绝不重复应用；重复删除不会误伤其他字符。
- **延迟处理（pending）**：收到操作时检查其依赖——insert 需要锚点字符已存在，delete 需要目标字符已存在。依赖缺失则放入 `pending` 队列；每当新操作整合完成后反复尝试排空队列，依赖一齐即自动补整合。所以“删除一个还没收到的字符”是安全的。
- **幂等交换**：`pullFrom(other)` 用版本向量只取自己缺失的操作；`sync` 是双向反熵交换。任何投递顺序、任何合并拓扑（环形、轮辐式）结果一致。
- **版本向量（VV）**：`{ [replicaId]: 已连续整合的最大 counter }`。乱序时不跨越空洞（收到 counter=3 而 1、2 未到时 VV 停在 0），连续段补齐后自动推进。VV 用于：判断已见操作、计算增量交换、以及推导 GC 检查点。

### 历史压缩（tombstone GC）的安全条件

tombstone 不能随意物理删除：迟到的旧操作可能仍引用它。引擎提供两级判定：

1. **知识屏障（检查点）**：`computeCheckpoint(replicasOrVVs, peers)` 计算全员版本向量的逐分量最小值 `C`（共同前沿）。`C` 被每个成员的 VV dominate，意味着**全体成员都已收到 ≤C 的所有操作**。一个 tombstone 满足 `canGarbageCollect` 当且仅当它是死节点、且它的 insert 与 delete 操作 ID 都被 `C` 覆盖。
2. **结构屏障（整棵死子树）**：`compact(C)` 只物理移除“**全部后裔也都是可回收 tombstone**”的节点。这保证没有任何存活节点需要挪动，RGA 全序与可见文本严格不变。若死节点下还挂着存活后裔（别人曾在该字符处继续插入），就保留该墓碑，等后裔也被删除并被后续检查点覆盖后再回收。

协调要求：各成员在**同一个检查点**上各自执行压缩（这是一个分布式安全屏障：所有成员都已见过 ≤C 的操作，此后不会再有引用那些节点的操作产生）。压缩前 `compact` 会校验本副本 VV dominate 检查点，否则抛错。

## 本地状态保存与恢复

- `replica.toJSON()` / `Replica.fromJSON(data)`：完整序列化（操作日志、节点树、版本向量、Lamport 时钟、pending、seen），树结构按边重建。
- `replica.save(path)` / `Replica.load(path)`：写入/读取本地 JSON 文件模拟进程重启。
- 恢复后的副本继续合并，结果与从未中断的执行**完全一致**；pending 操作也会持久化，依赖补齐后照常整合。
- 新成员加入：应从某成员的 `toJSON()` 快照初始化（全量状态拷贝），而不是只接收压缩后的增量日志——压缩后被回收的操作已不在日志中（快照即新基线）。

覆盖场景（31 个用例）：

- 单副本插入/追加/删除、越界钳制、中文与 emoji 多字节字符；
- 双副本：普通并发、**同一位置并发插入**（正反两种投递顺序结果一致）、并发插入与删除、双方删除不同/相同字符；
- **重复操作**：重复整批 / 重复单条 insert、delete，均不重复应用；
- **乱序投递**：锚点后到、洗牌批量投递与顺序投递结果一致；
- **延迟删除**：delete 先于目标 insert 到达，补齐后正确生效；
- 三/四副本多轮并发、Lamport 决胜、任意合并拓扑与随机 fuzz 收敛；
- **网络分区模拟**：分区期间两侧各自编辑、恢复后收敛；三分区轮辐式传播；
- 版本向量：空洞不推进、增量交换、共同前沿检查点；
- **历史压缩**：未达检查点不能压缩、整棵死子树规则、压缩后继续协同、超前检查点拒绝；
- **持久化**：内存快照往返、pending 持久化、本地文件保存/重启/再重启；
- 综合 fuzz：四副本 × 多轮随机编辑 + 随机丢包/乱序投递 + 中途全体快照重启，最终全量收敛。

## 设计取舍说明

- 文本片段在本地按 code point 拆成单字符操作，换取删除/锚点语义的简洁；批量插入仍整块连续。
- 为保顺序证明简单，GC 采用保守的“整棵死子树”规则；活跃文档下可回收大部分墓碑，极长的连续死链在尾部删除后即可整体回收。
- 所有“网络”行为都由调用方在本地编排（直接传对象、洗牌、丢弃、延迟），因此可以在一个测试进程里确定性地重放任意分区与故障。
